# CRM Analytics SQL proof: results

**Last full run on the real code: 128 passed, 3 failed, 0 not run.** The hand-calculated sample in contract section 9 matches exactly, including NEW median 5 with 5 completed stays. All SQL is valid. Two bugs were found:

- **B1, a wrong number:** New applications counts a soft-deleted person's applications when no filter is set (T8).
- **B2, a time limit:** at production size, Overview and the overall conversion trend hit the 8 s page limit (V3, V8). Launch-sized data passes.

Both fixes are written below and were tried around the real code without editing the repo: with `PROOF_TRY_FIXES=1`, T8 passes, the whole suite gives 122 passed and 0 failed, and every volume read takes about 2 s at most.

The SQL ran on real Postgres 16 (the dev `postgres:16` container), in a separate database named `analytics_proof`. The CRM's `default` database was never opened. No CRM server ran, so this proves the SQL and the numbers, not the CRM writing timeline rows. That still needs `fields.mjs` and `people.mjs` (see "Not proved here").

## Bugs

Line numbers were read at the last run. `crm-analytics-metrics.service.ts` is still being edited, so search for the names if they have moved.

### B1. New applications counts a soft-deleted person's applications when no filter is set

- **Failing check:** T8.
- **Where:** `packages/twenty-server/src/modules/analytics/services/crm-analytics-metrics.service.ts:1224`, `buildSubmissionScopeJoinSql`, used by `computeNewApplications` (line 840) and `readNewApplicationBuckets` (line 2072).
- **What happens:** with no person filter the query does not join people, so a submission whose person is soft-deleted still counts. Any person filter joins `scope` and drops it. Category rows always join, so they drop it too.
- **Exact result:** one live person and one soft-deleted person, one application each. `status: 'ACTIVE'` gives 1, no filter gives 2. Expected 1 both times.
- **Why it matters:** the headline figure disagrees with the same figure under a filter and with the Categories tab, and contract section 6 says `deletedAt IS NULL` everywhere. The `NEW_APPLICATIONS` trend has the same fault.
- **Proposed fix:** do not simply always join `scope`, because `public-form.service.ts:229` writes `personId: person?.id ?? null`, and an inner join would lose an application with no person (T28 guards this). Change the one relation all readers share, `buildApplicationSubmissionRelationSql` in `packages/twenty-server/src/modules/analytics/facade/crm-analytics-facade.service.ts:298-300`:
  ```sql
  SELECT s.id, s."personId" AS person_id, s."submittedAt" AS submitted_at
  FROM "workspace_x"."_formSubmission" s
  JOIN "workspace_x"."_crmForm" f ON f.id = s."formId"
  LEFT JOIN "workspace_x"."person" p ON p.id = s."personId"
  WHERE s."deletedAt" IS NULL AND f.name IN (...)
    AND (s."personId" IS NULL OR p."deletedAt" IS NULL)
  ```
  `buildSubmissionScopeJoinSql` can then stay as it is. The relation text in contract section 4 needs the same edit. Check `crm-analytics-facade.service.spec.ts`, 'reads custom tables, filtered on the application forms', against the new text.
- **Tried:** with `PROOF_TRY_FIXES=1`, T8 and T28 both pass.

### B2. Page statements hit the 8 s limit at production size, through nested loops over CTE scans

- **Failing checks:** V3 (Overview), V8 (overall conversion trend by month), on 43,000 people, 4,300 of them applied since tracking start, 43,000 moves. The viewer sees the tab's error state.
- **Where:** `packages/twenty-server/src/modules/analytics/services/crm-analytics-database.service.ts:36-39` (page settings) and `:59` (job connection). The statements most exposed are `buildStageClockCtes` (`crm-analytics-metrics.service.ts:432`) and `step_exit` in `buildFunnelCtes` (`:347`), but any statement over these CTEs can flip.
- **What happens:** Postgres has no statistics for a CTE's output, so its estimates collapse to a few rows when the real count is thousands, and it picks a nested loop that rescans a CTE for every row. From `sql-proof/volume-plans.txt`:
  - Overview, stage clock: `Nested Loop Left Join (... rows=28 ...) (actual ... rows=26462 ...)`, `Rows Removed by Join Filter: 540816295`. 40 s when allowed to finish.
  - Overall conversion trend, `step_exit`: `Nested Loop (... rows=1 ...) (actual ... rows=26 loops=5)`, `Rows Removed by Join Filter: 26909165`. 55 s when allowed to finish.
- **Why it matters:** the plan flips with row estimates, so it is not a smooth limit. 500 moves failed where 2,000 passed. A tab can start failing one day with no code change.
- **Proposed fix:** turn off nested loops and JIT for analytics statements only. In `runPageTransaction`, after the `statement_timeout` line, local to the transaction:
  ```ts
  await run(`SELECT set_config('enable_nestloop', 'off', true)`, []);
  await run(`SELECT set_config('jit', 'off', true)`, []);
  ```
  In `runJob`, before `work`, on the job's own connection, which is destroyed afterwards:
  ```ts
  await queryRunner.query('SET enable_nestloop = off');
  await queryRunner.query('SET jit = off');
  ```
  JIT must go too. A nested loop with no alternative (`unnest`, `a.rank >= f.rank`, reconcile's `LATERAL`) keeps the disabled-plan cost, which passes `jit_above_cost` and spends about a second compiling each statement: at 500 moves, the funnel read went from 0.4 s to 2.7 s with nested loops off alone, and to 0.3 s with both off. Contract section 4's page settings need the same two lines. CRM pools are not affected.
- **Tried:** with `PROOF_TRY_FIXES=1`, every read below passes, at every size tried.

## Observations, not failures

- **Reconcile limit (R5).** A person with no stored transition at all has nothing to compare, so a change in the CRM goes unseen. This is the limit the contract accepts in section 5.
- **`restored_count` above 0 does not prove lost events (R10).** Two members editing one person within 10 minutes keep separate timeline rows, and one can merge after the other is written. The rows then end on the wrong stage, and reconcile corrects it with one flagged row. The stored chain does end on the CRM's stage.
- **An application with no linked person (T28)** counts in the headline and in no category row, so Categories' New applications can fall short of the headline. The page does not say so.
- **`isStale` while the very first sync runs (Z11).** The code says false; contract section 5 reads "absent while a sync row exists", which would be true. The code's reading avoids a false stale banner during the first sync, so the contract sentence is the one to change.
- **Every statement costs about 40 ms on this machine,** even `SELECT now()`, while planning takes 1 to 5 ms. That is Docker Desktop's port forwarding, not the SQL, and it is most of this harness's run time.
- **The daily job holds `workspaceQueue`, which runs one job at a time.** The 160 s above is an 8-report catch-up at the largest size; with the fix it is 20 s.

## Not proved here

Nothing was blocked by a missing file: every service existed by the last run.

- **Real timeline rows, T1 to T11 in contract section 9.** They need the CRM server and worker. `fields.mjs` and `people.mjs` are written for that run, syntax checked with `node --check`, and not run. Each file's header gives its command. `people.mjs` writes `backdate.sql` for the `psql` step.
- **The real `WorkspaceOrmManager`, `UserVarsService` and metadata cache**, all faked here, and so the off-switch SQL in contract section 5.
- **`crons/`, `resolvers/`, `crm-analytics.module.ts`, guards and the UI.** None of them holds metric SQL; they need the server.
- **Production's stage values.** The config is still the provisional default from contract section 1, so these numbers prove the logic on those defaults. Altered-config checks C1 to C7 prove the paths the audit may switch on: reminders, aliases, a non-UTC zone, no limits, no success stage, the signed figure.
